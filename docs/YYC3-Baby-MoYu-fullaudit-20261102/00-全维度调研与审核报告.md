## 0. 项目整体画像

**一句话总结**：一套「Next.js 16 + React 19 + SQLite」的单体 Web 应用，围绕 0–3 岁婴幼儿家庭提供
「记录 → 评估 → 陪伴 → 庆祝」的成长守护闭环，工程质量门禁（类型/Lint/测试/构建/依赖审计/视觉回归）
已成型，但**AI 核心能力与多个内容模块仍停留在本地模拟层**，属「高质量骨架 + 半成品血肉」阶段。

**核心标签**：

| 标签 | 说明 |
| ---- | ---- |
| 🧱 单体 Next.js App Router | 页面 + API Routes 同仓（25 个端点），无独立后端服务 |
| 🗄️ SQLite（`node:sqlite`） | 9 张表、WAL、外键、真实落盘 `data/yyc3.db` |
| 🔐 认证已闭环 | JWT（access/refresh 分型）+ httpOnly Cookie + CSRF Origin 校验 + 限流 + 租户隔离 |
| 🎨 四主题设计令牌 | 暖阳 / 液态翡翠 / 赛博霓虹 / 极光（`data-theme`） |
| 🏅 30 枚徽章 | 8 分类 × 4 等级，声明式评估引擎（真实数据计算） |

| ⚠️ 数据双轨 | 档案/记录/作业走服务端；课表/日程/互动/视频走 localStorage |

## 二、深度维度分析（现状 · 问题 · 影响）

### 2.1 架构合理性

**现状**
- 三层清晰：`app/`（页面与路由）→ `lib/`（领域服务/数据/鉴权）→ SQLite；API 统一走 `lib/db/server.ts`（表名白名单 + JSON 列归一），底层 SQL 标识符全部经 `assertSQLIdentifier`。
- 认证链设计完整：access/refresh 类型声明不可互换、refresh Cookie 限 `/api/auth`、CSRF Origin 兜底、限流按 IP/邮箱/用户多维度。
- 混合路由（根中文 + `/en` 镜像）有明确防御点：避免 next-intl 重写全站导致 404（`middleware.ts` L26-L31）。

**问题**
1. **AI 层无统一网关**：`@ai-sdk/openai`（3 条路由）、BigModel（2 个服务）、fal.ai（1 条路由）、本地规则（2 条路由）四种实现分散，且缺少 provider 抽象与降级策略矩阵。
2. **数据层双轨**：4 类业务数据（课表/日程/互动/视频）走 localStorage，与 SQLite 主库并存，无同步策略。
3. **文档声明的 AI 引擎不存在**：`docs/developer/06-ai-engine.md` 列出 15 个模块并标「✅ 已接线」，实际 `lib/ai/` 仅 2 个文件，`lib/{growth,intelligence,ml,performance,voice}` 全为空目录。
4. **扩展性瓶颈**：进程内限流（`Map`）+ 文件型 SQLite + `next start` 单进程 = 横向扩容即失效（限流失效、WAL 跨机不可用）。

**影响**
- 新成员按文档实施会直接踩空（信任成本高，返工概率大）；
- 数据双轨导致「换设备丢数据」类投诉，且无法做跨端统计；
- 扩容时需要先做架构改造（外置缓存 + 数据迁移），不是配置级变更。

### 2.2 代码质量

**现状**
- 类型债已清零：`tsc --noEmit` 0 error（1.13s），`next build` 未启用 `ignoreBuildErrors`。
- API 层防御性编程到位：`pickFields` 白名单、`isChildOwnedBy` 归属校验、zod 入参校验（登录/生图/编排/评估/续写）。
- 错误处理：路由层统一 `try/catch` + 结构化 JSON；`ErrorBoundary` + `global-error-handler` + 前端错误上报端点。
- 注释规范：文件头 `@fileoverview/@description/@author/@version` 统一，关键安全决策带原因。

**问题**
1. 56 条 lint warning 长期挂起（`any` 家族、`no-floating-promises`、React Compiler 兼容族），规则被降级为 `warn`（`eslint.config.js` L37-L70），无回潮阻断机制。
2. 24 处 `console.log` 残留（`app/api/error-report/route.ts` L117/L149 等），与 winston 体系并存，生产噪音。
3. 测试有效性不均：`__tests__/hooks/useAIChat.test.ts` L67 **在测试文件内自行定义 `useAIChat`**，生产代码中并不存在该 hook → 用例通过但零覆盖，属自证型测试。
4. 13 个 `<img>` 缺 `alt`（`app/videos/page.tsx` L110/L158/L226、`app/books/page.tsx` L125/L162、`components/books/BookReader.tsx` L177/L273 等）。
5. README 声称「axe 0 违规阻断」，但仓库**未安装 axe-core / @axe-core/playwright**，无障碍仅有 64 处手写 ARIA 属性。

**影响**
- 类型安全与安全编码基线可信，可作为团队范式；
- 但「测试数 257」含水分，「WCAG 2.2 AA 已验证」缺乏工具证据 → 对外宣称需校准，否则易失信。

### 2.4 性能风险

**现状（实测）**
- 首页首字节/首屏 49 ms（本地生产模式）；`/en` 8 ms；构建 1,151 ms；45 页静态预渲染 240 ms；单元测试 392 ms。
- 客户端静态资源 1.7 MB JS（最大 chunk 228 KB）；`public/` 18 MB（单图 624 KB 顶图、多张 400–500 KB 角色图）。
- 索引齐备：14 个索引覆盖 `child_id / user_id / recorded_at / due_date / status / subject`。

**问题**
1. **无分页/无上限**：`GET /api/growth-records` 返回该用户全部记录（按孩子循环查询，N 次 SQL）；`/api/children`、`/api/homework` 同样全量返回。
2. **N+1 查询**：`app/api/stats/route.ts` L41-L43 对每个孩子各发一次 `count`；成长记录按孩子逐个 `listRows` 后内存排序（L30-L37）。
3. **首屏 JS 偏重**：`framer-motion` 被 45 个文件引用、**0 处 `next/dynamic`**，重组件（图表/编辑器/视频工坊）全部进主包；`images.unoptimized: true` 使图片无优化。
4. 无性能监控指标（无 Lighthouse/Web Vitals 采集），仅 `@vercel/speed-insights` 已安装但未接入。

**影响**：单用户 1,000 条记录时首屏数据接口将达数百 KB + 多次查询；中低端移动端首屏 JS 解析成本明显。属「可用但不可扩展」。

### 2.5 安全风险

**现状（正向）**
- 实测：匿名访问 `/api/children`、`/api/ai/chat` 均 401；敏感页未登录 307 重定向；`/zh` 307、未知路径 404；安全头（CSP/X-Frame-Options/nosniff/Referrer-Policy/Permissions-Policy）全部生效。
- 登录限流实测有效（错误密码第 6 次起 429）；refresh 令牌不可当 access 使用；登出后 Cookie 立即失效（实测 401）。
- 密钥仅服务端（`BIGMODEL_API_KEY` 无 `NEXT_PUBLIC_` 前缀）；SQL 全部参数化 + 表名/列名白名单。

**问题**
| 风险 | 位置 | 说明 | 实测 |
| ---- | ---- | ---- | ---- |
| 匿名可写错误上报 | `app/api/error-report/route.ts` | 无认证、无限流、无体积限制；可向服务端日志写入任意 `stack`（日志注入/磁盘消耗），并可触发 Slack 外发 | 匿名 POST **200** |
| CSP 允许内联脚本 | `next.config.mjs` L39 | `script-src 'self' 'unsafe-inline'`，XSS 纵深防御弱 | 响应头已确认 |
| 限流键可伪造 | `lib/rate-limit.ts` + 各 route 取 `x-forwarded-for` | 若前置代理未覆写该头，攻击者可轮换 IP 绕过限流 | 代码核查 |
| 日志含 PII | `lib/logger/server.ts`、登录日志 | `email`/`userId`/错误堆栈落盘，无脱敏与保留期策略 | 代码核查 |
| 开发密钥文件 | `data/.jwt-dev-secret` | 本地存在（0o600、已 gitignore）；生产未配 `JWT_SECRET` 会拒绝启动（设计正确） | `ls -la data` |
| 测试账号 | 种子 `parent@yyc3.com / demo123456` | 生产模式跳过种子（正确），但文档广泛公开该口令 | `README.md` L182 |

**影响**：核心数据面（认证/租户/IDOR）经实测可信；风险集中在「辅助端点 + 边缘配置」，属可快速收敛项。

### 2.6 可维护性

**现状**
- 文档体系完整：11 篇开发者文档 + 用户手册 + 开源四件套 + Issue/PR 模板 + 5 份会话记录。
- 自动化成熟：四道门禁 + OSV 周扫 + 四主题视觉回归（darwin/linux 分平台基线）+ Dependabot 分组。
- 部署可复现：`bun install --frozen-lockfile` + `PORT/JWT_SECRET` 显式注入，实测可起。

**问题**
1. **部署文档与资产不一致**：`docs/developer/08-deployment.md` 提及 Docker，但仓库无 `Dockerfile`/`docker-compose.yml`；实际仅支持本地 `next start`。
2. **环境变量文档缺项**：`.env.example` 缺 `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`FAL_KEY`、`CSRF_TRUSTED_ORIGINS`、`CSRF_REQUIRE_ORIGIN`、`ADMIN_EMAIL`、`DATABASE_URL`，而代码中均在读取 → 按文档部署即 AI 500。
3. **排障入口不足**：无 `/api/health` 健康检查端点；日志需进服务器查看（无集中采集）。
4. **二次开发成本**：数据双轨 + 三套 AI 供应商 + 文档失真，导致新成员需「读码反推文档」，首次上手预计 ≥ 2 人日。

**影响**：可维护性的短板不在代码，而在「文档 = 事实源」这一约定被破坏。

## 八、结论

1. 这不是一个「玩具项目」：认证、数据隔离、CI、依赖治理与视觉回归的完成度高于多数同规模开源项目。

3. 建议的对外表述：**「工程化成熟的成长记录 + 部分 AI 能力的早期版本」**，而非「完整 AI 陪伴系统」。
